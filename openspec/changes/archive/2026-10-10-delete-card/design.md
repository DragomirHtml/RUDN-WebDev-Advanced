## Context

Текущая архитектура:
- **API-слой:** `client/src/api/cards.ts` — `fetchCards()` и `createCard()` через `fetch` к `/api/cards`
- **Кэш-менеджмент:** TanStack Query (`useQuery` в `App.tsx`, `useMutation` + `invalidateQueries` в `NewCardForm`)
- **Сервер:** JSON Server (`json-server db.json --port 3001`), прокси через Vite `/api/*` → `localhost:3001`
- **Компоненты:** `App.tsx` → `BoardColumn` → `BoardCard` (однонаправленный поток данных)
- **Типы:** `Card { id, title, isDone, isUrgent? }`

JSON Server уже поддерживает `DELETE /cards/:id` из коробки — бэкенд-код не нужен.

## Goals / Non-Goals

**Goals:**
- Добавить возможность удаления карточки с подтверждением
- Обновить UI автоматически через TanStack Query после успешного DELETE
- Минимально изменить существующие файлы, без рефакторинга

**Non-Goals:**
- Рефакторинг `BoardCard` → `BoardColumn` → `App.tsx` (перенос состояния, хуки, контекст)
- Toast-уведомления, анимации удаления, undo-откат
- Миграция с JSON Server на полноценный бэкенд

## Decisions

### Decision 1: Где разместить мутацию удаления

**Выбор:** Создать `deleteCardMutation` в `App.tsx`, передать колбэк `onDelete` через пропсы в `BoardColumn`, затем в `BoardCard`.

**Сравнение вариантов:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. В `App.tsx`** (выбрано) | Мутация рядом с `useQuery(["cards"])` — один источник правды; `invalidateQueries` вызывается в одном месте; паттерн повторяет `NewCardForm` | Пропинтинг `onDelete` через `BoardColumn` |
| **B. В `BoardColumn`** | Мутация ближе к карточкам, не нужно пробрасывать из `App` | `BoardColumn` уже содержит логику фильтрации — перегрузится; дублирование кэша (нужен `useQueryClient`); нарушает принцип «данные управляются наверху» |
| **C. В `BoardCard`** | Карточка сама себя удаляет | `BoardCard` — presentational-компонент; не знает о кэше; нарушает однонаправленный поток данных |

**Обоснование:** Вариант A соответствует существующему паттерну `NewCardForm` (мутация + `invalidateQueries` в одном компоненте-контейнере) и принципу React: данные и мутации управляются на верхнем уровне, потомки получают колбэки через пропсы.

### Decision 2: Подтверждение удаления — `window.confirm()` vs кастомный диалог

**Выбор:** `window.confirm()`

**Сравнение вариантов:**

| Критерий | `window.confirm()` (выбрано) | Кастомный модал |
|---|---|---|
| **Зависимости** | 0, нативный API | Требует создания компонента `ConfirmDialog` + CSS |
| **Сложность** | 3 строки кода | ~150 строк (диалог, overlay, aria, анимации) |
| **Скорость реализации** | Мгновенно | Требует дизайна, верстки, тестирования |
| **UX** | Стандартный диалог браузера | Можно стилизовать, анимировать |
| **Доступность** | Нативная (скринридеры, клавиатура) | Нужно реализовывать вручную (aria-modal, focus trap) |
| **Соответствие спеке** | ✅ Требует подтверждения — выполнено | ✅ Тоже выполнено |

**Обоснование:** Для оценочного задания KAN-2 приоритет — минимальное решение, закрывающее требование спеки. `window.confirm()` покрывает все 4 требования без дополнительного кода. Кастомный модал — это overengineering для данной задачи; его можно добавить позже как улучшение (не входит в spec).

### Decision 3: Пессимистичное vs оптимистичное обновление

**Выбор:** Пессимистичное (как в `NewCardForm` — ждём `onSuccess` перед `invalidateQueries`).

**Обоснование:** `createCard` в проекте уже использует пессимистичный паттерн. JSON Server быстрый (локальный), поэтому задержка незаметна. Это сохраняет консистентность стиля.

### Decision 4: API-функция `deleteCard`

**Выбор:** Добавить `deleteCard(id: string): Promise<void>` в `client/src/api/cards.ts` — параллельно с `fetchCards` и `createCard`.

**Обоснование:** Единый API-файл — текущая конвенция проекта. `DELETE /api/cards/${id}` — стандартный REST-эндпоинт, который JSON Server поддерживает из коробки.

## Risks / Trade-offs

| Риск | Вероятность | Митигация |
|---|---|---|
| `window.confirm()` блокирует UI-поток | Низкая | Критично только для долгих операций; DELETE быстрый |
| Нет сообщения об ошибке при сбое DELETE (первая итерация) | Средняя | В спеке есть требование «Ошибка удаления отображается» — добавить в tasks |
| Пропинтинг `onDelete` через `BoardColumn` | Низкая | Один проп, типизированный `(id: string) => void`, не усложняет интерфейс |

## Open Questions

Нет. Все технические решения разрешены в рамках утверждённой спеки.
